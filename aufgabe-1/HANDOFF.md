## Part D – results to write up in `docs/measurements.md`

All data comes from `tools/measure.sh` (Bash, run from WSL; CSVs in `docs/measurements/`). Decisions made with the user: ideal injected values, 5 runs each, emulator limits stated honestly; accelerometer flat / tilted 30° / free fall; barometer step size measured first, then 1–3 floors; GPS walk + jitter + jump at 2.8 m/s; energy via the app's CPU time.

- **Accelerometer** (`accelerometer.csv`): exact in all runs. Flat (0, 0, 9.80665) → |a| 9.807 m/s² = 1.000 g. Tilted 30° (4.903, 0, 8.493) → same values, |a| still 9.807. Free fall (0, 0, 0) → 0.000. Expected values: SensorEvent docs ("flat on a table … +9.81", "free-fall … 0 m/s²"), trigonometry for the tilt.
- **Barometer step size** (`barometer-steps.csv`): the emulator rounds pressure to the nearest multiple of 0.125 hPa (switching points at 1013.1875 and 1013.0625).
- **Barometer floors** (`barometer.csv`): set 1012.890 / 1012.530 / 1012.169 hPa (3 / 6 / 9 m by the inverted platform formula), received 1012.875 / 1012.500 / 1012.125, app shows Δh 3.12 / 6.25 / 9.37 m. Formula values for the received pressures: 3.122 / 6.246 / 9.371 m, so the app is exact; the deviation from 3 / 6 / 9 m is the emulator's rounding (≈ 1 m per 0.125 hPa step).
- **GPS** (`gps.csv`, final run): walk 111.2 m in all 5 runs (expected 111.19 m, WGS84 meridian), 0 jitter steps counted, distance unchanged after the jump. In run 5 the "rejected" log line is missing because the app logs at most one line per second; the unchanged distance shows the rejection. Single steps alternate 10.9 / 11.3 m: the emulator seems to place positions on a ~0.42 m grid (the resolution of a 32-bit float at 48°; the exact mechanism is not confirmed). `gps-first-run.csv` holds the first run (111.2 / 100.3 / 111.2 / 100.3 / 111.2 m), caused by a pacing error in the script (`ai-errors.md` entry 15), fixed before the final run.
- **Event rate** (`rate.csv`): `GAME` 50.0 Hz (app and Android's own event record). `NORMAL` 15.0 Hz instead of the requested 5 Hz (one reading 24.2 Hz). Cause: the sensor runs at the fastest rate any client requests. Other clients seen in `dumpsys sensorservice`: `WindowOrientationListener` (screen rotation; believed to use `SENSOR_DELAY_UI` ≈ 15 Hz – **verify with a source before writing it down**), `FaceDownDetector`, and Google's location service, which briefly registered at 20 ms (explains the 24.2 Hz outlier).
- **CPU** (`cpu.csv`): mean 3.20 % at `GAME` (3.27 / 3.12 / 3.21), 2.67 % at `NORMAL` (2.68 / 2.73 / 2.61): −17 % CPU for −70 % events, because the fixed work (UI snapshot every 100 ms, processing chain) stays. Emulator on a PC CPU, so only the ratio transfers; screen and GPS dominate real consumption.
